1. Authentication Flow (Microsoft SSO)

1.1 How Auth Works

The application uses Microsoft Azure AD (AAD) SSO with an OAuth2 proxy layer. The session is maintained via a _oauth2_proxy cookie on the application domain.

1.2 Bootstrap Process

StepWhat Happens
1Run npm run auth:bootstrap from project root
2Real Chromium browser opens and navigates to the app URL
3You complete Microsoft SSO login manually (including MFA if required)
4Playwright waits for the post-login redirect back to the app
5All session cookies are saved to playwright-load/auth-state-ms.json

1.3 Session Reuse in Tests

ToolHow Auth State Is Used
Playwrightbrowser.newContext({ storageState: AUTH_STATE_PATH }) — context starts pre-authenticated
k6 browseropen(AUTH_STATE_PATH) at init time, context.addCookies(AUTH_COOKIES) before navigation

1.5 Session Expiry

Note: Microsoft AAD session tokens typically last 8–24 hours depending on tenant policy. Always re-run npm run auth:bootstrap at the start of each test day.

2. Cloudflare Bot Protection Bypass

2.1 How Cloudflare Is Handled

Cloudflare bot protection is bypassed automatically because both Playwright and k6 browser use real Chromium instances, not HTTP API calls.

Cloudflare CheckHow It Is Bypassed
JavaScript challengeReal browser executes the challenge automatically
Browser fingerprintReal Chromium matches expected browser fingerprint
TLS fingerprint (JA3)Real Chromium TLS matches expected client hello signature
Cookie validation (__cf_bm)Captured during auth:bootstrap and injected with auth cookies
Mouse/interaction patternsNot checked for page loads; only checked for form submissions

2.2 Cloudflare Cookies in Auth State

Cookie NameDomainRotation Interval
__cf_bm.dev.apps.lilly.comEvery 30 minutes
__cf_bm.dev.fdl.lilly.comEvery 30 minutes
__cf_bm.dev.unex.lilly.comEvery 30 minutes
Important: The __cf_bm cookie rotates every 30 minutes. VUs that started before rotation continue to work. New VUs starting after rotation may get challenged. For long-running tests (>30 minutes), some VUs may see Cloudflare challenges — real browsers handle these automatically.

3. Consent Banner Handling

3.1 Why Special Handling Is Required

The Transcend consent manager uses a closed Shadow DOM (mode: "closed"). This means:

  • element.shadowRoot returns null from external JavaScript
  • Standard CSS selectors cannot pierce into the shadow DOM
  • k6 browser cannot click buttons inside it via normal DOM interaction

3.2 Solution Per Tool

ToolApproachHow It Works
PlaywrightShadow DOM wait + evaluatewaitForSelector waits for host to attach, then clears consent cookies, reloads, and clicks Accept/Reject inside shadow DOM via page.evaluate()
k6 browserDirect storage writeClears existing tcm cookie and tcmConsent localStorage, writes the correct consent payload directly, then verifies both are readable — bypasses shadow DOM entirely
